# RB-01 — Regional Failover

## 1. Purpose

This runbook defines the controlled procedure for failing the PaySecure Gateway platform over from the primary AWS Region, Mumbai (`ap-south-1`), to the disaster recovery Region, Hyderabad (`ap-south-2`).

The procedure is designed for a regional impairment where the Mumbai environment can no longer reliably serve production traffic.

### Recovery Objectives

- Target RTO: < 5 minutes
- Target RPO: < 1 minute
- Primary Region: Mumbai (`ap-south-1`)
- Recovery Region: Hyderabad (`ap-south-2`)
- DNS: Amazon Route 53
- Primary application endpoint: Mumbai ALB
- Secondary application endpoint: Hyderabad ALB

---

## 2. Trigger Conditions

Initiate this runbook when one or more of the following conditions occur:

1. Complete or widespread Mumbai regional outage.
2. Multiple critical AWS services become unavailable in Mumbai.
3. EKS workloads cannot maintain production availability.
4. Aurora primary database becomes unavailable and cannot recover within the RTO.
5. Regional networking prevents application access.
6. AWS or internal incident command declares Mumbai unsuitable for continued production service.
7. Automated monitoring indicates sustained regional failure and the incident commander approves failover.

Do not initiate regional failover for an isolated pod, node, Availability Zone, or single-service failure that can be handled within Mumbai.

---

## 3. Roles and Responsibilities

| Role | Responsibility |
|---|---|
| Incident Commander | Authorizes failover and coordinates the incident |
| SRE / Platform Engineer | Validates EKS, ALB, networking, and application health |
| Database Engineer | Validates Aurora and DynamoDB replication/failover |
| Network Engineer | Validates Transit Gateway, VPN, PrivateLink, and routing |
| Security Engineer | Validates PCI/CDE controls and security boundaries |
| Application Owner | Validates application transactions and APIs |
| Communications Lead | Communicates incident status and recovery progress |

No individual should independently redirect production traffic without incident-command authorization.

---

# 4. Preconditions

Before executing the failover:

- Hyderabad infrastructure must exist and be healthy.
- Application images must be available through ECR or the approved recovery deployment mechanism.
- Aurora replication must be healthy.
- DynamoDB replication must be healthy.
- MSK replication must be within the RPO target.
- Required secrets and certificates must exist in Hyderabad.
- Hyderabad ALB must have a healthy target group.
- Route 53 failover records must exist.
- Health checks must be operational.
- Operators must have the required AWS IAM permissions.

---

# 5. Failover Procedure

## Step 1 — Declare the incident

**Owner:** Incident Commander  
**Estimated time:** 15 seconds

Declare a regional outage and assign the incident roles.

Record:

- Incident ID
- Start timestamp
- Detection timestamp
- Current primary Region
- Target recovery Region
- Incident commander
- RPO/RTO target

Do not change production traffic yet.
