# RB-01 - Complete Primary Region Failure

## 1. Scenario Identification

- **ID:** S1
- **Category:** Infrastructure
- **Severity:** P1-Critical
- **Primary:** Mumbai (`ap-south-1`)
- **Recovery:** Hyderabad (`ap-south-2`)
- **Affected components:** EKS, ALB/WAF, Aurora Global Database, DynamoDB, Redis, MSK, networking, Route 53, payment processing.
- **Targets:** RTO under 5 minutes; RPO under 1 minute.

## 2. Detection Mechanism

Page the Incident Commander when payment API success rate is below 99.5% for 2 minutes, Route 53 health checks fail in 3 consecutive 10-second checks, and at least two independent Mumbai control-plane probes fail. A single endpoint failure is not sufficient evidence of regional failure.

## 3. Impact Assessment

At peak, 1,200 TPS and 45,000 merchants may be affected. Planning revenue exposure is approximately INR 37.5 lakh per hour. The IC records failed, timed-out, and unknown in-flight transactions separately; unknown transactions are never blindly retried and are reconciled by idempotency key and bank status.

## 4. Immediate Response (0-2 minutes)

1. **Incident Commander (15s):** Open the P1 incident, freeze deployments, and record incident ID and timestamps.
2. **Primary on-call SRE (15s):** Page database, network, security, application, and communications leads.
3. **SRE (20s):** Run `aws sts get-caller-identity` and confirm the operator account and incident permissions.
4. **SRE (30s):** Run `aws cloudwatch describe-alarms --state-value ALARM --region ap-south-1` and preserve the output as evidence.
5. **Application lead (30s):** Stop new non-idempotent retries and mark requests interrupted after the failure boundary as `UNKNOWN`.

## 5. Diagnostic Steps (2-5 minutes)

6. **SRE (20s):** Run `aws ec2 describe-availability-zones --region ap-south-1 --query 'AvailabilityZones[].State' --output table`.
7. **SRE (20s):** Run `aws eks list-clusters --region ap-south-1 --output table`; compare with the Hyderabad result.
8. **Network engineer (30s):** Run `aws elbv2 describe-load-balancers --region ap-south-1 --query 'LoadBalancers[].State.Code' --output table`.
9. **DBA (30s):** Run `aws rds describe-global-clusters --global-cluster-identifier $env:PAYSECURE_GLOBAL_CLUSTER_ID --query 'GlobalClusters[0].{Status:Status,Members:GlobalClusterMembers}' --output json`.
10. **IC (20s):** If Mumbai control-plane calls fail but Hyderabad is healthy, classify as regional failure; if only the inter-region path fails, stop and invoke RB-05 for a partition.
11. **DBA (20s):** If Aurora lag is greater than 60 seconds or the target member is not `available`, abort promotion and invoke the data-loss approval path.

## 6. Failover Procedure (5-15 minutes)

12. **DBA (30s):** Confirm the Hyderabad cluster identifier with `aws rds describe-global-clusters --global-cluster-identifier $env:PAYSECURE_GLOBAL_CLUSTER_ID --query 'GlobalClusters[0].GlobalClusterMembers' --output json`.
13. **IC (15s):** Approve promotion only when the DR API is healthy and the current writer is unavailable or fenced.
14. **DBA (60s):** Run `aws rds failover-global-cluster --global-cluster-identifier $env:PAYSECURE_GLOBAL_CLUSTER_ID --target-db-cluster-identifier $env:PAYSECURE_DR_DB_CLUSTER_ID --region ap-south-2`.
15. **DBA (30s):** Verify promotion with `aws rds describe-global-clusters --global-cluster-identifier $env:PAYSECURE_GLOBAL_CLUSTER_ID --query 'GlobalClusters[0].GlobalClusterMembers' --output json` and confirm exactly one writer.
16. **Platform engineer (30s):** Scale the DR node group with `aws eks update-nodegroup-config --cluster-name $env:PAYSECURE_DR_CLUSTER --nodegroup-name $env:PAYSECURE_DR_NODEGROUP --scaling-config minSize=24,maxSize=36,desiredSize=24 --region ap-south-2`.
17. **Platform engineer (20s):** Verify readiness with `kubectl --context $env:PAYSECURE_DR_KUBE_CONTEXT -n paysecure get pods -o wide` and `kubectl --context $env:PAYSECURE_DR_KUBE_CONTEXT -n paysecure rollout status deployment/payment-api --timeout=30s`.
18. **Network engineer (45s):** Submit the approved Route 53 change using `aws route53 change-resource-record-sets --hosted-zone-id $env:PAYSECURE_HOSTED_ZONE_ID --change-batch file://route53-dr-change.json`.
19. **Network engineer (30s):** Wait for propagation with `aws route53 wait resource-record-sets-changed --id $env:PAYSECURE_ROUTE53_CHANGE_ID` and verify `Resolve-DnsName api.paysecure.example`.
20. **Application lead (30s):** Run a non-financial synthetic transaction and confirm API success, Aurora write/read, idempotency record, and settlement event without using live card data.
21. **IC (30s):** If any verification fails, stop traffic increase, restore the previous DNS record only if Mumbai is reachable, and declare Hyderabad not ready.

## 7. Communication Protocol

**Engineering:** `[P1][S1][{incident_id}] Mumbai regional failure - {status}; impact {tps}/{merchants}; action {action}; next update {time}; war room {link}`

**Management:** `PaySecure P1 update: Mumbai is unavailable. Hyderabad promotion is {status}. Current RTO clock {elapsed}; estimated recovery {eta}; financial exposure {amount}; IC {name}.`

**Merchants/banks:** `PaySecure Service Advisory: payment processing may be delayed for {methods}. Hyderabad recovery is {status}. Do not duplicate unknown transactions; retain the original idempotency key. Next update {time}.`

**Regulators:** `Incident {id}; detected {timestamp IST}; affected region ap-south-1; quantified impact {value}; RPO observed {lag}; actions {actions}; status {status}; contact {CISO}.`

## 8. Verification and Validation

- `curl --fail-with-body --max-time 10 https://api.paysecure.example/health/ready` returns HTTP 200 and readiness JSON.
- `kubectl -n paysecure get deployment payment-api transaction-processor settlement-engine` shows available replicas equal to desired replicas.
- `aws rds describe-global-clusters` shows one Hyderabad writer and replication state complete.
- A synthetic idempotent test confirms exactly one transaction record and one settlement event.
- Monitor success rate, P99 latency, Aurora lag, MSK consumer lag, DNS answers, and duplicate-key alarms for 15 minutes.

## 9. Rollback Procedure

Rollback is allowed only if Hyderabad validation fails and Mumbai is reachable and fenced. The IC stops new traffic, the DBA prevents dual writers, the application lead drains Hyderabad connections, and the network engineer restores the last known-good Route 53 record. Re-run the health and single-writer checks before reopening traffic. If Mumbai is not reachable, keep Hyderabad isolated and invoke incident command; never point DNS at an unverified region.

## 10. Post-Incident Review

Within 2 business days, reconstruct detection, approval, promotion, DNS, and validation timestamps; reconcile every unknown transaction by idempotency key and bank response; attach CloudTrail, Route 53, Aurora, Kubernetes, and synthetic-test evidence; perform a five-whys review; record owners and due dates for corrective actions; and complete RBI, NPCI, PCI DSS, and CERT-In notification checks as applicable.
