# RB-12 — Cascading Microservice Failure

## 1. Scenario Identification

| Field | Details |
|---|---|
| **Runbook ID** | RB-12 |
| **Scenario** | Cascading Microservice Failure |
| **Category** | Application / Infrastructure |
| **Severity** | P1-Critical |
| **Primary Region** | AWS Mumbai (`ap-south-1`) |
| **DR Region** | AWS Hyderabad (`ap-south-2`) |
| **Affected Components** | EKS, microservices, Istio, ALB, Aurora PostgreSQL, DynamoDB, ElastiCache Redis, MSK Kafka |
| **Target RTO** | < 5 minutes |
| **Target RPO** | < 1 minute |
| **Primary Objective** | Stop cascading failures, isolate unhealthy services, preserve transaction integrity, and restore stable application processing |

### Scenario Description

A cascading microservice failure occurs when failure or severe degradation in one service propagates through service dependencies and causes additional services to fail.

Examples include:

- A database connection pool exhaustion causing API failures
- A Kafka consumer backlog causing downstream processing delays
- Redis failure causing excessive database traffic
- A failed payment service causing transaction retries
- Excessive retries creating additional load
- One unhealthy dependency causing multiple services to become unavailable

The primary objective is to **break the failure chain** rather than immediately restarting every service.

# 2. Detection Mechanism

## Primary Alerts

| Alert | Metric / Signal | Threshold |
|---|---|---|
| API Error Rate | HTTP 5xx percentage | >5% for 2 minutes |
| API Latency | p95 request latency | >2 seconds for 3 minutes |
| CPU Saturation | EKS node/pod CPU | >85% for 5 minutes |
| Memory Saturation | Pod memory utilization | >85% |
| Pod Restarts | Container restart count | >3 in 5 minutes |
| Kafka Lag | Consumer lag | >10,000 messages |
| Aurora Connections | DB connections | >80% of configured capacity |
| Redis | Cache hit rate | <80% or abnormal errors |
| Request Rate | TPS | >150% of baseline |
| Circuit Breaker | Open circuit count | >5 services |
