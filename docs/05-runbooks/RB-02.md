# RB-02 — Regional Failback

## 1. Purpose

This runbook defines the controlled procedure for returning PaySecure Gateway production traffic from the disaster recovery Region, Hyderabad (`ap-south-2`), to the original primary Region, Mumbai (`ap-south-1`).

Failback must only occur after Mumbai has been fully restored, validated, synchronized, and approved for production use.

### Recovery Objectives

- Target RTO: < 5 minutes
- Target RPO: < 1 minute
- Current production Region: Hyderabad (`ap-south-2`)
- Original primary Region: Mumbai (`ap-south-1`)
- DNS: Amazon Route 53

---

## 2. Important Principle

Failback is a controlled operation.

Do not immediately switch DNS back to Mumbai simply because AWS services in Mumbai become available.

The recovery team must first:

1. Restore Mumbai.
2. Validate infrastructure.
3. Establish replication.
4. Synchronize application and database state.
5. Confirm data integrity.
6. Perform the database switchover.
7. Validate Mumbai production readiness.
8. Move production traffic.
9. Continue monitoring.

For Aurora Global Database, a controlled switchover is designed for planned operations and can synchronize the secondary before changing primary roles, providing zero-data-loss behavior when the required conditions are met.

---

## 3. Trigger Conditions

Begin this runbook when:

1. Mumbai regional services have recovered.
2. Hyderabad is currently serving production traffic.
3. Incident Command determines that Mumbai is ready to become primary again.
4. Required data replication paths are operational.
5. Mumbai infrastructure has passed recovery validation.
6. The application and security teams approve failback.

Do not begin failback if Mumbai remains unstable.

---

## 4. Roles and Responsibilities

| Role | Responsibility |
|---|---|
| Incident Commander | Authorizes failback |
| SRE / Platform Engineer | Validates EKS, ALB, networking, and infrastructure |
| Database Engineer | Validates Aurora and database synchronization |
| Network Engineer | Validates DNS and regional networking |
| Security Engineer | Validates security and PCI/CDE controls |
| Application Owner | Validates APIs and transactions |
| Communications Lead | Communicates failback status |

---

# 5. Preconditions

Before failback:

- Mumbai EKS cluster is healthy.
- Mumbai ALB is healthy.
- Mumbai Aurora cluster is available.
- Aurora replication from Hyderabad to Mumbai is healthy.
- DynamoDB replication is healthy.
- MSK replication is healthy.
- Required Redis state/configuration is available.
- Required secrets and certificates are available.
- KMS keys are available.
- Route 53 records are configured correctly.
- Mumbai application images are available.
- Security controls have been validated.
- No unresolved critical incident exists in Mumbai.

---
